1. Entity-Relationship (ER) Diagram

The system uses MongoDB Atlas with 5 collections. All data collections reference the User collection via a userId field, creating a single-tenant-per-user architecture.

Figure 1 — Entity-Relationship diagram showing all 5 MongoDB collections and their relationships
ℹ️ Note
MongoDB does not enforce foreign keys at the database level. The userId references are maintained at the application layer via Mongoose's ref: 'User' and validated in API route handlers using session-based ownership checks.

💡 Why Cache?
The global.mongoose caching pattern is critical for Next.js — without it, every hot-reload in development would create a new database connection, exhausting the Atlas connection pool.

Figure 4 — Three-layer user uniqueness: Identity → Authentication → Data isolation

Isolation Enforcement Summary

LayerMechanismDetails
Email uniqueness unique: true + lowercase: true MongoDB creates a unique index. No two accounts share an email.
ObjectId (_id) Auto-generated by MongoDB 12-byte globally unique ID (timestamp + machine + process + counter)
Password hashing bcrypt.hash(password, 10) Even identical passwords produce different hashes
JWT session NextAuth jwt callback Every request carries the user's _id in the token
Data ownership userId: { ref: 'User' } API routes filter all queries by userId: session.user.id
Admin approval isAdminVerified flag New accounts blocked until super-admin approves
2FA (OTP) Email OTP, 10-min expiry Fresh OTP required after 1-hour grace period
💡 Single-Tenant-Per-User
The system behaves like a single-tenant-per-user model. Each pharmacist sees only their own inventory, billing records, and rack layout — completely isolated from other pharmacists — all enforced by the userId foreign key on every query.
